# Диагностика телеметрии и варианты следующего эксперимента

Версия: 2026-09-30. Итог: в текущей облачной среде не установлен работоспособный путь модельных вызовов с проверяемыми измерениями. Во время этой диагностики новых модельных вызовов и платных API-запросов не было.

## Точный блокер запуска

Предыдущее описание среды только для чтения было неполным. Две ограниченные диагностики нового запуска App Server с параметрами `sqlite_home` и `log_dir` в доступных для записи каталогах теперь устанавливают два разных уровня:

1. Переопределение SQLite работает: в диагностическом каталоге созданы новые файлы SQLite. Рабочая папка также доступна для записи. Локальный CLI поддерживает эти настройки; они не являются механизмом переноса управляемого облачного хранилища. [Справочник конфигурации](https://learn.chatgpt.com/docs/config-file/config-reference).
2. Затем запуск вызывает `bwrap`. Его дочерний процесс открывает `/proc/self` как каталог и пытается выполнить `openat(fd, "uid_map", O_RDWR|O_CLOEXEC)`, получая `-1 EROFS (Read-only file system)`. Дочерний процесс и App Server завершаются с кодом 1 до инициализации протокола. Обе диагностики воспроизвели этот сбой.

Следовательно, оставшаяся проблема — ограничение настройки вложенной песочницы/пользовательского пространства имён на `/proc/self/uid_map`, а не неверный выбор доступной для записи папки проекта. Замена папки проекта или пути SQLite не исправляет наблюдаемый системный вызов. Мы не отключали песочницу, не перемонтировали файловые системы, не меняли разрешения пространств имён, не повышали доступ, не переназначали каталог учётных данных, не копировали credentials и не изучали сохранённые/скрытые сессии. Диагностика трассировала имена запускаемых программ и файловые операции, а не содержимое учётных данных или модельный трафик. Полные локальные трассы не публикуются; очищенная фактическая запись находится в [свидетельствах диагностики](../experiments/2026-09-30/telemetry-diagnostic.json).

## Какая телеметрия существует и что доступно здесь

Локально изучена сгенерированная схема установленной версии `0.159.0-alpha.3`. Она включает следующие поля:

| Интерфейс | Поля или события схемы | Интерпретация |
|---|---|---|
| Ответ запуска потока | `model`, `modelProvider`, `reasoningEffort`, `serviceTier` | Разрешённая конфигурация потока; сохранять вместе с запрошенной |
| Событие смены модели | `fromModel`, `toModel`, `reason`, `turnId` | Учитывать сообщённое провайдером изменение модели |
| Использование токенов потока | `last`, `total`; `inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`, `reasoningOutputTokens`, `totalTokens` | Записывать фактически полученные поля каждого хода; наличие поля в схеме не означает заполненную квитанцию |
| Лимиты аккаунта | `rateLimits`, `rateLimitsByLimitId` | Потребление по окнам, возможно грубое и совместно используемое |
| Встроенный инструмент сотрудничества | Запуск принимает модель/усилие; возвращаемые записи раскрывают идентичность задачи, статус и текст | Получение использования ресурсов или фактической модели в этой сессии не предоставлено |

Официальная [документация App Server](https://learn.chatgpt.com/docs/app-server) описывает `thread/tokenUsage/updated`, `model/rerouted`, `account/rateLimits/read` и `account/usage/read`. Сводки токенов аккаунта и суточные интервалы не позволяют приписать расход одному эксперименту при другой активности аккаунта. Работающий сервер мог бы предоставить полезные сведения от провайдера, а не криптографическое доказательство физического исполнения конкретной моделью. Разрешение снимка модели и отсутствующие ответы либо смены модели всё равно потребуют явного учёта.

[Документация субагентов](https://learn.chatgpt.com/docs/agent-configuration/subagents) описывает настройку моделей и усилия; она не устанавливает экспорт телеметрии именно для этого встроенного runner. В доступных контрактах инструментов не найдено действия получения токенов, фактической модели или оплаты. Общие возможности App Server нельзя приписывать этому другому интерфейсу. Неподдерживаемые серверные endpoints или скрытые сессии для восполнения пробела не использовались. Отсутствие относится к доступному здесь интерфейсу и не означает отсутствия телеметрии у OpenAI вообще.

## Что устанавливают имеющиеся 6/6

Каждый из двух сохранённых объектов ответа проходит все шесть фиксированных проверок, а независимый автономный аудит подтверждает эталоны. Запрошенные конфигурации и точные запросы записаны. Это подтверждает базовое исполнение с ответом без инструментов и правильность на конкретных входах.

Это не устанавливает общую эквивалентность моделей, высокую надёжность принятых результатов, относительную задержку, токенную эффективность, экономию подписки или проверенную идентичность фактически применённой модели. Шесть ответов объединены в один ответ каждой запрошенной модели и не являются шестью независимыми запусками. W→E повторно использует W и ни разу не передавала задачу. Фактических токенов для ретроспективного восстановления нет, а опубликованные временные окна остаются грубыми границами наблюдения. Мы не выдумываем токены и не подставляем время другого запуска.

## Минимальные способы разблокировать измерения

| Вариант | Необходимое изменение | Что можно измерить | Текущий статус |
|---|---|---|---|
| Платформа предоставляет встроенный runner с измерениями | Раскрыть разрешённую модель/смены модели, категории использования и время завершения каждого запуска, плюс снимки квоты | Реальные токены встроенного запуска; подписку только с предоставленной точностью | Такого вызываемого интерфейса здесь нет |
| Платформа поддерживает инициализацию песочницы App Server | Предоставить поддерживаемую среду с работающим пространством имён и доступными для записи каталогами состояния; сохранить обычную подписочную авторизацию | Конфигурацию потока, события использования и снимки лимитов аккаунта | Требуется поддержка среды/платформы; локальный обход не предпринимался |
| Пользователь предоставляет разрешённый работающий endpoint CLI/App Server | Поддерживаемая подключённая среда со своим штатным входом; без копирования credentials | Те же события с учётом фактической версии сервера и доступов | Endpoint не предоставлен и не создавался |
| Отдельно разрешённый API-микроэксперимент | Явное разрешение расходов и безопасно настроенный API-доступ в одобренной среде | Модель ответа API, использование и экономику API; не включённую квоту подписки | Только предложение; не запускалось |

До новых подписочных модельных вызовов сначала проверить инициализацию, список моделей и лимиты чтением без модельного хода. Затем потребовать от небольшой заранее заданной пробы сведения о модели/смене модели и использовании; при отсутствии полей остановиться. Одни счётчики токенов не устанавливают преобразование во включённую квоту. Изолировать или учитывать параллельную активность аккаунта и использовать идентификаторы окон и интервальные оценки с учётом точности квоты.

## Предлагаемый API-бюджет, не разрешение

Предлагаемый предел одобрения: **$2.00 расходов API**, без покупки кредитов и изменения настроек аккаунта. Это условная оценка для текстовых вызовов Standard, обычного контекста, без региональной наценки и платных инструментов. До любого вызова подтвердить актуальные тарифы и обеспечить ограничения. Источники: [Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), [Sol 6.1](https://developers.openai.com/api/docs/models/gpt-6.1-sol).

Ограниченная схема использовала бы восемь фиксированных задач, каждую в отдельном новом контексте. На задачу: один исходный W и один прямой E; резерв не более одного исправления W и одной передачи E из той же контрольной точки провала W. Добавить по одной пробе телеметрии на модель. Это не более 17 запросов W и 17 E, всего 34, включая сбои и повторы. Отключить автоматические повторы SDK; неоднозначные сбои расходуют слот запроса и свой максимальный бюджет до сверки.

Ограничить каждый полностью собранный запрос 8,000 входных токенов и `max_output_tokens=4000`, включая рассуждения. До отправки проверить входную границу поддерживаемым способом. Для консервативной оценки весь вход оценивается по полному тарифу записи кэша, без повторного прибавления обычного входа:

`C_W_max = (8000*0.125 + 4000*0.50)/1e6 = $0.003`

`C_E_max = (8000*2.50 + 4000*10.00)/1e6 = $0.060`

`C_fixture_max = 17*0.003 + 17*0.060 = $1.071`

Предлагаемый предел $2.00 оставляет $0.929 нераспределённого резерва; он не разрешает дополнительные запросы. Это условные границы, а не наблюдаемые расходы или жёсткий лимит всего аккаунта. До каждого запроса резервировать полную верхнюю оценку; остановиться, если квитанции, тарифы или ограничения не удаётся сверить. Налоги, прежние обязательства аккаунта и посторонняя активность не входят в оценку этих API-вызовов. Покупка не предлагается. [Контроль стоимости рассуждений](https://developers.openai.com/api/docs/guides/reasoning) описывает ограничения генерируемых токенов; незавершённые ответы тоже расходуют ресурсы и должны учитываться как нерешённые, а не молча исключаться. Предел 4,000 токенов сам может ограничивать качество и должен оставаться одинаковым и явным для политик.

## Нейтральный выбор следующих задач

До любого нового сравнительного вызова зафиксировать восемь случаев: планирование зависимостей с циклами и равенствами, ограниченную оптимизацию, семантику NULL/дубликатов SQL, отмены операций журнала и крайние случаи разбора/округления. Требовать независимо реализованные эталоны, нетривиальные конкурирующие решения и выполнение всех обязательных условий. Не использовать пробные модельные ответы для отбора случаев или ожидаемых победителей. Сначала опубликовать задачи/хеши, случайно выбрать и записать порядок выполнения, проверить каждый результат и сохранить все таймауты, усечения и неудачные попытки в знаменателях. Если все случаи снова окажутся решены, сообщить это; не заменять лёгкие случаи молча после наблюдения результатов моделей.

Это предложение следующего исследования, а не выполненный второй тест или окончательно подготовленный набор задач. Следующее необходимое решение — какую измеримую среду предоставить. Имеющееся разрешение на подписку не разрешает предложенный платный API-бюджет.

## Обязательный допуск по телеметрии каждого вызова

**Текущий путь не проходит этот допуск. Новое экономическое сравнение запускать нельзя.** До сравнительных вызовов продемонстрировать серверный usage или документированные события среды с привязкой каждого вызова к `task_id`, `strategy`, фактическому `model_id`, `attempt`, `stage`, `input_tokens` и `output_tokens`. Запрошенной модели или самоотчёта модели недостаточно. Токены чтения и записи кэша записывать отдельно, если они предоставлены; недоступные категории должны быть `null`/unavailable, а не выдуманными нулями.

Сохранять безопасные исходные usage-поля, документированное происхождение события, связь с ответом/ходом, единицы и семантику агрегирования. Установить, включают ли входные totals чтение/запись кэша, а выход — reasoning; вычитать только включённые взаимоисключающие категории и не прибавлять рассуждения дважды. Не выводить эту связь только из имён полей. При наличии сохранять накопительные поля и поля хода с границами сброса, чтобы не начислять расход повторно. Записывать смены модели; остановить атрибуцию, если фактическую модель нельзя установить. Включать неудачные вызовы, повторы, консультации, эскалации и весь переданный/повторённый контекст. Общее исполнение W входит один раз в физический итог и один раз в каждую использующую его логическую политику. Оценки токенов по длине и синтетические квитанции не заменяют отсутствующие серверные данные. Проверка схемы не подтвердила семантику живых квитанций.

## Пригодность SWE-rebench и готовность контейнеров

[SWE-rebench-leaderboard](https://huggingface.co/datasets/nebius/SWE-rebench-leaderboard) лучше подходит как следующий кандидат для работы с репозиторием: карточка предоставляет базовые коммиты, описания проблем, Docker-образы задач и `FAIL_TO_PASS`/`PASS_TO_PASS`. В наборе также есть патчи решений и тестов, требующие отдельной закрытой границы проверки. Карточка сообщает о готовых образах; это не подтверждает, что каждый выбранный образ загрузится и пройдёт контрольные проверки здесь.

Проверки инфраструктуры только чтением обнаружили Docker client и server 28.4.0 на Linux x86_64; daemon сообщает 5 CPU и 18,882,699,264 байт памяти, в рабочем пространстве свободно примерно 29.82 GiB. Эти наблюдения не гарантируют квоты benchmark. Harbor и Podman не установлены. Установка, загрузка образов, создание контейнеров, выполнение тестов и покупка ресурсов не проводились. Наличие Docker не исправляет заблокированный App Server и не разрешает монтировать credentials в контейнер. Размеры образов, доступ к registry, ограничения ресурсов тестов и реальное исполнение контейнеров остаются непроверенными.

Предложенный [июльский split Harbor 2026 года](https://hub.harborframework.com/datasets/ibragim-badertdinov/swe-rebench-07-2026/latest) не загрузился через браузерный инструмент; прямой HTTP-доступ получил proxy 403. Запрос метаданных ревизии Hugging Face также заблокирован на этом прямом пути. **Ни неизменяемая ревизия, ни digest образа не подтверждены.** Не запускать по плавающему `latest`. До отбора записать неизменяемую ревизию dataset/Harbor, точные ID задач, базовые коммиты, ревизию harness и digest образа каждой задачи. Проверить достаточность подходящих задач; не подменять месяц молча, если июльский набор мал. Более новые задачи снижают некоторые риски знакомства с решениями, но не доказывают отсутствие contamination. Исключить из отложенной оценки примеры, патчи решений/тестов которых были показаны карточкой при этом обзоре.

SWE-bench Verified использовать только для smoke-test. [Аудит OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/) выявил признаки contamination и дефекты тестов: существенные проблемы были у 59.4% проверенной сложной подвыборки из 138 задач, а не у 59.4% всего benchmark. Это обосновывает независимые проверки harness и осторожность меток, но не доказывает отсутствие дефектов у SWE-rebench.

## Калибровка, отложенная оценка и граница проверки

Выделить **8–12 calibration задач**, затем отдельные **40–60 eval задач**; не начинать ни один этап до прохождения допуска телеметрии и инфраструктурных проверок. По возможности разделить по репозиториям/семействам ошибок, удалить дубликаты и записать выбор до наблюдения результатов моделей. По калибровке можно глобально настроить рабочую маршрутизацию; зафиксировать политику, пределы и ID задач до открытия отложенных результатов. Сорок–шестьдесят задач остаются пилотом, а не доказательством высокой надёжности.

Моделям предоставляются только проблема, базовая рабочая копия и разрешённые существующие/публичные проверки. Не передавать gold patches, test patches, идентификаторы скрытых тестов, вывод финального grader или подсказки/историю с решением. Хранить файлы проверки вне доступных агенту монтирований; проверить образы и историю Git на утечки решений. Независимый контроллер проверяет контрольные прогоны base/gold в средах только для grader. Gold — контроль оценки, а не вход агента. Сбои и нестабильность инфраструктуры отмечать отдельно, сохраняя количества и расходы по заранее объявленным правилам исключения.

Маршрутизация использует только разрешённые рабочие свидетельства: публичные проверки, воспроизводимые проверки из требований, ограниченные критерии прогресса/таймаута. Зафиксировать каждого кандидата до запуска скрытого финального grader на изолированной копии. Не возвращать его результат в исправление W, передачу E или консультацию. Если позднее явно запрошено сравнение маршрутизации по скрытому grader, обозначить его **oracle-routing baseline** и исключить из выводов о применимой на практике политике. Общую формулировку первого пилота о передаче при провале нужно для SWE-задач уточнить до этого видимого контроля.

## Отдельный сценарий бюджета SWE-пилота

Предыдущее предложение $2 относится только к микроэксперименту с ответами без инструментов; это **не** реалистичное бюджетное обязательство для benchmark репозиториев. Для планирования предполагаются тарифы Standard API, без наценок/инструментов, не более 100,000 суммарных входных токенов и 20,000 генерируемых токенов на траекторию роли по всем вызовам и передачам контекста. Эти ограничения нужно обеспечивать по проверенным квитанциям и консервативному резервированию с явными лимитами вызовов/времени; они не предсказывают типичный расход SWE.

При консервативной оценке всего входа по записи кэша траектория W стоит не более `(100000*0.125 + 20000*0.50)/1e6 = $0.0225`; E — `(100000*2.50 + 20000*10.00)/1e6 = $0.45`. Заложить до двух траекторий W и двух E на задачу: исходный W, условное исправление W, прямой E, условную передачу E. Это даёт `$0.945` на задачу.
